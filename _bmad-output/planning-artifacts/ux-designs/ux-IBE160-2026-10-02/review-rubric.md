# Spine Pair Review — Jaunt

## Overall verdict

The pair is source-extractable for most downstream work — flows, tiering, and the core component vocabulary all resolve cleanly, and the frontmatter `sources:` fix means both files now trace to real PRD paths. But DESIGN.md has a genuine, self-flagged hole (zero inline links to any file in the new `mockups/` folder, including the one mock that exists specifically to show the "Quiet Streets" map treatment DESIGN.md spends a full paragraph describing), two Should-tier components (the preference slider, the catch-up row) have behavior in EXPERIENCE.md but no visual spec anywhere in DESIGN.md, and one cross-reference (`{character-jarrod}`) doesn't resolve under the spec's own path rule. None of these block a human reader who already knows the project, but an automated resolver or a cold story-dev consumer would stall on at least two of them.

## 1. Flow coverage — strong
Checked: `sources:` → prd.md §2.2 names UJ-1 (Vilde) and UJ-2 (Steve); addendum.md contributes no new UJs/FRs requiring flows (it's Post-V1 ideas only). EXPERIENCE.md's Key Flows has one flow per UJ, each with a named protagonist, numbered steps, an explicit `**Climax:**` beat, and an italicized edge-case/failure path at the end.
### Findings
- **low** Flow 1 and Flow 2's closing lines carry visible editorial voice ("her own neighbourhood just became worth walking again"; "exactly the... resolution PRD UJ-2 calls for") rather than plain behavioral narration — see Finding 6 below for the general pattern. (EXPERIENCE.md Key Flows, Flow 1 step 13, Flow 2 step 9). *Fix:* trim the payoff sentence to what happened, not what it means.

## 2. Token completeness — adequate
Checked: all 20 `colors`, all 9 `typography` roles, all 8 `rounded` scale steps, and all 6 `spacing` steps in DESIGN.md's frontmatter against every `{path.to.token}` reference in both files' prose.
### Findings
- **medium** `colors.sage-light` (`#CBDAB9`) and `colors.logo-field` (`#FDFEFA`) are defined in frontmatter but never mentioned in the Colors prose — no "why this exists, where it's used" story, unlike every other color. Both are real, active colors (the splash screen's layered hillside parallax and the sampled logo-reveal background in `mockups/flow-01-setup.html` lines 89–91, 234, 651). The Launch splash is a named IA surface in EXPERIENCE.md with its own State Patterns row, but DESIGN.md has no component entry for the splash scenery at all. *Fix:* add a short Colors entry for both, or a "Launch splash" paragraph in Components.
- **medium** No WCAG contrast ratio is stated anywhere for the system's primary load-bearing pairing (`{colors.ink}` on `{colors.cream}`/`{colors.surface}`) — EXPERIENCE.md's Accessibility Floor explicitly says so itself ("no WCAG contrast ratio has actually been calculated... should be checked before shipping, not assumed"). Flagged honestly rather than silently assumed, which is the right instinct, but it means a story-dev consumer has no actual target to build against. *Fix:* run the check once and record the ratio, even if it's just confirming the obvious.
- **low** The `spacing` scale (xs–2xl) is fully defined but never referenced via `{spacing.X}` anywhere — every component's padding in frontmatter is a literal px string (`'12px 24px'`, `'13-14px vertical, 8px horizontal'`). DESIGN.md's own Layout & Spacing section already admits this ("treat the frontmatter spacing tokens as an accurate description of current practice, not a pre-existing locked system") — self-aware, so not a hidden gap, but it means the token layer and component layer are currently disconnected. *Fix:* either wire components to `{spacing.X}` or drop the scale from frontmatter until it's load-bearing.

## 3. Component coverage — adequate
Checked: every component name in DESIGN.md's frontmatter `components` map, every bolded component header in DESIGN.md.Components prose, and every row in EXPERIENCE.md.Component Patterns, cross-matched both directions.
### Findings
- **high** The landmark ↔ hidden-gem **preference control** (FR-4, Should-tier, has its own row in EXPERIENCE.md.Component Patterns and its own row in Scope Tiers) has **no visual spec anywhere in DESIGN.md** — no frontmatter token, no Components prose paragraph. DESIGN.md mentions "landmark/hidden-gem track" only once, in passing, as a usage example for the Sage color (DESIGN.md Colors, line 171). A developer has no spec for the slider's track, thumb, fill behavior, or Balanced-default visual state. *Fix:* add a `preference-control` (or similar) component entry.
- **medium** The **catch-up row** (EXPERIENCE.md.Component Patterns: "a checkbox-style row per stop, pre-checked if marked Visited... unchecked rows carry a soft 'forgot?' hint") has no DESIGN.md counterpart. It's structurally distinct from the numbered-circle "Stop row" DESIGN.md does spec — no numbered marker, has a checkbox, has hint-text styling. *Fix:* add a short Components paragraph, or explicitly note it reuses Stop row's layout with a checkbox substitution.
- **low** `button-outline` exists in DESIGN.md frontmatter and is used (the Route Review "Re-Jaunt" button, DESIGN.md Components "Equal-weight button pair" paragraph) but is never named by token in EXPERIENCE.md's Component Patterns row for that same pair — only `button-secondary-fill` and `button-primary` are bracketed. *Fix:* add the third variant to the row's parenthetical.
- **low** The time wheel-picker's visual spec lives under DESIGN.md's "Card" component, but its behavioral rule lives only in EXPERIENCE.md's Interaction Primitives, not in Component Patterns where every other component's behavior sits. Not missing, just inconsistently placed. *Fix:* optional — add a one-line Component Patterns row for symmetry.

## 4. State coverage — adequate
Checked: every IA surface in EXPERIENCE.md against its State Patterns table rows.
### Findings
- **medium** FR-24 ("use my current location" for starting point) has no State Patterns row for permission denial, despite its sibling FR-14 (continuous tracking) getting a dedicated row ("Active walking — no GPS (Must-tier fallback)"). FR-1's own Consequences say a denied/failed FR-24 request "falls back cleanly to map-tap/named starts; it is never a dead end" — but EXPERIENCE.md never states what that fallback actually looks like (silent revert? a toast? nothing is said). - **low** Mid-walk permission *revocation* (as opposed to initial denial) isn't addressed — does the head marker just vanish and the "Location off" pill appear instantly, or is there a transition? Minor; likely falls out of the existing no-GPS row by extension. *Fix:* one clause would close it, not urgent.

## 7. Inheritance discipline — adequate
Checked: `sources:` frontmatter resolution, UJ/FR naming verbatim-ness, glossary consistency, component-name consistency, and whether every `{path.to.token}` in EXPERIENCE.md actually resolves inside DESIGN.md's frontmatter.
### Findings
- **medium** `{character-jarrod}` (used in EXPERIENCE.md's Component Patterns header "Jarrod (`{character-jarrod}`)") does not resolve under the stated cross-reference rule ("the path follows the YAML structure"). In DESIGN.md's frontmatter, `character-jarrod` is nested two levels down as a child of `components:`, so the correct path is `{components.character-jarrod}` — the bare form is a root-level lookup that doesn't exist. Every other component reference in the same table (`{components.bubble}`, `{components.chip}`, etc.) uses the correct prefixed form; this one is the sole outlier. *Fix:* add the `components.` prefix.
- Confirmed clean otherwise: both `sources:` paths resolve to real files; UJ-1/UJ-2 names and persona details match prd.md §2.2 verbatim; FR numbers cited throughout EXPERIENCE.md (FR-1, 4, 9, 10, 11, 13, 14, 16–20, 22–24) match PRD content accurately on spot-check, including the two corrected-2026-10-03 items (FR-9's "more time never less," FR-3's "surprise me" cross-topic behavior); Engagement-State glossary terms used identically to prd.md §3; all other `{components.X}`/`{colors.X}`/`{typography.X}` references resolve.
