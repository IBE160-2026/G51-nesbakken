Closing Jaunt's frontend-wiring gap

Six decisions that make the tested backend (planner.py / ai.py / services.py) and the finalized UX spines (DESIGN.md / EXPERIENCE.md) buildable without two people building incompatible halves.

2026-10-07 6 decisions · fixed twice under review Source: ARCHITECTURE-SPINE.md

One-way dependency: browser → API → planner → {AI, routing}. Nothing downstream calls back up, and the browser never sees a provider key.

The six decisions

AD-1Map renderingBase layer built & verified

We moved the map library from Leaflet to MapLibre, with OpenFreeMap as a free, keyless, limitless tile source — now, before anything else gets built on top of the map, since this is the cheapest point in the whole project to make that change. The custom color palette from the design isn't done yet; today's map uses a free plain style as a placeholder.

Prevents
One builder styling raster tiles while another assumes vector tiles exist; many-of-a-kind features (route line, amenity dots) built as individual DOM elements instead of one data layer.
Rule
MapLibre GL JS pinned 5.6.1 (v6 drops the plain-script-tag bundle this project relies on) · OpenFreeMap positron style · data-driven features use GeoJSON layers, one-off image content (Jarrod's head, a stop photo) uses Marker({element}).
Known exception
The existing catalogue-pin loop already renders one DOM marker per place — ported 1:1 from Leaflet to preserve behavior. Not retroactively required to change; the rule binds new features.
AD-2State ownership

The Python server never remembers anything between requests. One planning request returns everything; the browser's own local storage remembers your current walk, so a refresh doesn't lose your place. Visit history lives in a different storage slot, so ending a walk never wipes your history by accident. "End trip" only actually fires once the end-of-walk catch-up and summary screens finish — not the moment you tap "End Jaunt" — so a refresh during wrap-up still recovers. The Visited checkbox itself only works during an active walk, never while just previewing a stop beforehand.

Prevents
Server-side session state creeping in; a reload silently losing an in-progress trip; a stop previewed before the walk even starts getting recorded as genuinely visited.
Rule
Backend fully stateless. Active trip → its own localStorage key, cleared only when wrap-up completes or the user returns to setup. Visit history (AD-6) → a separate key, untouched by that action. The Visited control is context-gated: disabled/hidden outside an active walk.
AD-3AI content timing

Every stop's "fun fact" is written by AI all at once, when the route is first planned — not one by one as you tap through during the walk. Chosen specifically so the walk keeps working if your phone loses signal mid-route. If one stop's fact fails its own fact-check, only that stop falls back to plain source text; the rest of the route is never thrown away over it.

Prevents
A lazy per-stop content call that assumes connectivity mid-walk, incompatible with a trip meant to be complete and cached offline.
Rule
Content generation runs synchronously at plan time. Payload shape is binding: each stop carries id, order, content, and a structured attribution reference (source_type/source_title/source_url) — never a flat string with no source field.
Failure path
A per-stop grounding-check failure falls back to the raw source_excerpt, never a whole-route failure.

Corrected 2026-10-07: the grounding check itself isn't a small extension of existing code. Today's AI validation only checks that JSON parses and the chosen key was actually offered — it has no ability to judge whether generated prose is really supported by the source text. That detector doesn't exist yet and is real, substantial, unbuilt work — recommended as an early prototype task, with real supported/unsupported examples, before it's treated as a safe assumption.

AD-4Preference signal

The landmark-vs-hidden-gem slider doesn't get turned into some invented Python score. It's handed straight to the AI as part of the same judgment call it already makes about relevance — because "how well-known is this place" is a qualitative call, not arithmetic, and that's the line Python/AI already draw everywhere else in this project.

Not true yet: the AI prompt doesn't currently even receive the source title/type it would need to judge this well — that has to be added, not assumed already there.

Prevents
A Python-invented "prominence" heuristic competing with AI's own judgment of the same signal.
Rule
No new Python field. Preference travels as one continuous numeric value (matching the mock's slider, not a 3-value enum) straight into AI's prompt.
AD-5Replace / Re-Jaunt

Rejecting a stop and asking for a different one doesn't just blindly re-ask and hope — the requirements explicitly warn that wouldn't guarantee a new result. The rejected stop gets added to an exclusion list for the rest of that walk, and the route is re-checked for feasibility before it can be approved again.

Known, accepted trade-off: Re-Jaunt excludes every stop in the rejected route, not just the combination. A menu with routes {A,B} and {A,C} loses the valid {A,C} after rejecting {A,B}. Kept on purpose — Re-Jaunt is the clean-break tool, the separate per-stop removal (FR-11) is the precise one.

Prevents
A "replace" that's just an unchanged re-call to the planner; confusing this trip's rejects with AD-6's cross-trip history.
Rule
excluded_ids is a hard filter, session-local, cleared by end-trip — a different list from AD-6's history. Since the backend holds no state, the browser resends the full list every time, never just the newest addition.
AD-6Visit history

Your history of past visits and favourites lives in the browser, in its own separate spot from the current walk. It's a soft hint, not a hard rule — AI leans toward places you haven't seen, but a favourite can still resurface. It never flat-out blocks a place from coming back. Corrected 2026-10-07: the original schema only tracked a favourite flag, which actually lost the distinction the requirements require between a place you were only shown, one you previewed, and one you confirmed you actually visited.

Also reconciled: the PRD originally promised this data would "never" reach a server at all. Revised to a V1-scoped promise (nothing is stored server-side in V1; a transient per-request send is fine, same as the location-coordinate precedent) so a future account system isn't architecturally ruled out.

Prevents
A server-side history store; collapsing the four Engagement States into one "seen" flag (FR-17 explicitly prohibits this); hard-filtering visited/favourited places when the UX explicitly wants favourites to resurface.
Rule
Separate localStorage key from the active trip. Shape: a list of {id, state, favourited} — state is one of proposed/opened_engaged/visited_completed, favourited independent. Sent with the planning request as a transient, soft AI-weighting signal — never persisted server-side in V1.

Decided not to decide yet — and why that's the honest call

Visit-history retention. AD-6 settles where history lives, not how long it lives there or whether a user can clear it — genuinely undecided (PRD Open Question 7).

"Time remaining" display. From the original budget, or a live estimate from current position? The second needs a backend capability that doesn't exist yet (PRD Open Question 20).

Replace strategy. AD-5 settles the exclusion mechanism; whether a fresh AI suggestion or the next-best shortlisted option is still open (PRD Open Question 2).

Attribution UI. OSM, the routing provider, Wikipedia, NSW Heritage, Inner West Council all need crediting — a content/UI task, not an architecture fork.

Logging. Not addressed at all by this spine. Not assumed to be unnecessary — just genuinely not decided yet.

Sizing the actual UI build. The PRD itself flags that no sprint plan has ever assigned time to building this frontend, given the compressed timeline. This spine fixes the rules that UI must follow — scheduling the build is the next skill's job, flagged here as urgent.

Topic coverage, confirmed by checking the real catalogue. There is exactly 1 ready History stop and 1 ready Architecture stop against the planner's 2-stop minimum — those two topics cannot produce any route today. Not an architecture problem; a data-coverage gap needing its own task.
