Custom styling: fork OpenFreeMap's base style JSON and recolor/hide layers via Maputnik (free visual editor, live preview) to approximate DESIGN.md's palette, rather than hand-writing the MapLibre style spec from scratch. User's explicit call: willing to spend the extra build effort for a meaningfully better result rather than defaulting to the safest/cheapest option; this overrides CLAUDE.md's general 'keep it simple' lean for this one decision, logged explicitly so it reads as a deliberate trade-off, not scope creep.

- (decision) AD-2 [state ownership]. Binds: every endpoint and screen across the multi-step flow (setup, loading, route review, walking, end). Prevents: one builder adding Flask server-side session state while another assumes the backend is stateless, or a reload silently losing an in-progress trip with no recovery path. Rule: backend stays fully stateless (fits the already-ratified 'no database' constraint and no-accounts V1 scope) - one POST /api/plan (name TBD at API-design time) returns the complete route+stops+content; follow-up actions (replace a stop, mark visited) are separate stateless requests taking current state as input. ADOPTED refinement per user: the frontend persists the active trip (planned route, stops, visited markers) to localStorage so an accidental refresh doesn't lose progress; the app provides an explicit 'end trip' action that clears that saved state. No server memory involved either way - this is purely a client-side resilience layer on top of the stateless backend, not a architecture change to AD-2's core rule.

- (decision) AD-3 [AI content-generation timing]. Binds: ai.py's content-generation function (FR-19, not yet built) and the plan-time API response shape. Prevents: one builder wiring content generation as a per-stop-open lazy call while another assumes the full trip payload (route+stops+content) is complete and cacheable after one planning request - these are incompatible shapes for the same localStorage-persisted trip (AD-2). - (decision) AD-4 [preference-signal mechanism, FR-4]. Binds: how the landmark/hidden-gem preference actually influences stop selection. Prevents: one builder inventing a Python-computed 'prominence' heuristic (e.g. keyed off source_type) while another assumes AI alone judges it from the real content/source it already sees - two different signals that could rank the same shortlist differently. Rule: no new Python-computed prominence field. The preference value (Balanced/landmark-leaning/hidden-gem-leaning) passes straight into AI's existing selection prompt alongside each candidate's real source_type/source_title/content; AI leans its pick accordingly as part of the same qualitative judgment call it already makes. Matches the architecture boundary already ratified in docs/architecture-plan.md: Python does facts/arithmetic, AI does qualitative judgment, never the reverse.
