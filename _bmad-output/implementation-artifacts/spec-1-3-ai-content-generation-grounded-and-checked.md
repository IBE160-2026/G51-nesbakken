## Intent

**Problem:** `ai.py` only selects which stops form a route; nothing generates the actual per-stop content a user reads, and the product's core trust promise (grounded, never fabricated) has no mechanism at all yet - not content generation, not a grounding check, not the contextual-source lookup AD-3 names.

**Approach:** Add batched content generation (one AI call per route, not per stop) plus a two-tier grounding check to `ai.py`, backed by a new human-curated `data/contextual_sources.json` seed file accessed only through one swappable lookup function. A stop whose content fails generation or either grounding tier falls back to its raw source excerpt - the route is never discarded over this.

**Revised 2026-10-20 (Codex review, user's explicit choice - this supersedes the original rule-based-only plan):** the rule-based check was prototyped first and validated against real generated content and hand-fabricated bad examples (6/6 correct across 3 runs) - but Codex then produced concrete counterexamples proving it cannot catch a fabricated *claim or relationship* that introduces no new date or name (e.g. "Michael Snape designed this church" against the source "By Michael Snape." - the name is real, the relationship is invented). Verified directly, confirmed real. Per AD-3's own built-in escalation path ("escalating to a model call only if a prototype proves it insufficient"), and the user's explicit choice when asked, grounding is now two-tier: the rule-based check stays as a cheap pre-filter (skips the real check's cost for content already obviously bad), and a second, genuinely independent LLM-based semantic check (`check_grounding_semantic()`, still one batched call per route, not per stop) is the actual gate - content is only ever shown once that second check positively confirms it. See Design Notes for both the rule-based prototype's validated design/limitation and the semantic check's design.

## Boundaries & Constraints

**Always:** Content generation is exactly one batched AI call per route (every stop in one request), never one call per stop; the semantic grounding check is likewise exactly one batched call per route for everything that survives the cheap pre-filter, never one call per stop. Both grounding tiers are reusable as-is for Epic 3's later walk-summary content (same generic signature: text + source list in, bool out - nothing stop-specific baked into either). **Each stop's grounding check (both tiers) and generation prompt use only that stop's own evidence (its source_excerpt + whatever contextual sources were looked up for it) - never the batch's pooled text from other stops** (Codex review 2026-10-20: a batched multi-stop call must not let one stop's content "borrow" a fact that's only true of a different stop's source material). A stop's final attribution lists only sources the model explicitly declared drawing from, validated against what was actually offered - never every source merely offered, never an invented or borrowed one (Codex review 2026-10-20: attribution must reflect sources actually used, not just available). Contextual Source content is never phrased or implied as specific to the Stop it's blended into. Content is shown only once the semantic check positively confirms it - the rule-based check alone is never sufficient grounds to show content.

**Never:** No bulk/automated contextual-source retrieval - the lookup function's V1 body is a simple filter over the small seed file; the function boundary exists so that can be swapped later without touching generation, the check, the payload shape, or callers (architecture AD-3). No change to `planner.py` or `select_stops()` - this story adds new functions to `ai.py`, it doesn't touch stop selection. No integration into a live planning endpoint - that's Story 1.4's job; this story's deliverable is the `ai.py` functions Story 1.4 will call. No per-stop semantic grounding calls - always batched per route, same cost-minimization reasoning as generation itself.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Rich source excerpt, grounded generation | A stop with a long, detailed `source_excerpt` | Generated content passes the grounding check and is used, with attribution listing its own source | N/A |
| Thin source excerpt (real catalogue examples) | `source_excerpt` like `"By Michael Snape."` or `"church in Newtown, New South Wales"` | Content stays short/simple rather than padded with invented detail; still passes grounding if genuinely unembellished | N/A |
| Generated content contains a fabricated date or name | AI output includes a number or named entity absent from that stop's own evidence | Rule-based pre-filter fails for that stop; falls back to raw `source_excerpt`, single-entry attribution - the semantic call is never spent on it | N/A |
| Generated content fabricates a claim/relationship with no new date or name | e.g. a real name reused with an invented relationship ("Michael Snape designed this church") | Passes the rule-based pre-filter but fails the semantic check; falls back to raw `source_excerpt` the same way | N/A |
| Whole batched call fails or times out | Network/API error, malformed response | Every stop in that route falls back to its raw `source_excerpt` - the route is still returned, never discarded | N/A |
| Response missing a requested stop's entry | AI's JSON omits one `stop_id` that was requested | That one stop falls back to raw excerpt; others in the same successful response are unaffected | N/A |
| Two-stop batch, only one stop has a relevant Contextual Source | e.g. a `history`-topic stop and a `public_art`-topic stop in the same route - both `history` and `architecture` have a seed entry, `public_art` does not (corrected 2026-10-20, Codex review: the matrix originally named history/architecture here, but both actually have entries) | The `public_art` stop gets `get_contextual_sources()` returning `[]` and is generated/checked from its own excerpt alone - never borrows the other stop's contextual source or evidence | N/A |
| Cross-stop leakage check | Stop A's generated content (hand-constructed to contain a fact true only of Stop B's source text, in the same batch) | Grounding check fails Stop A - its own evidence set never includes Stop B's text | N/A |
| `surprise_me` route (no single topic) | Multiple topics possible across the route's stops; no seed entry is tagged `surprise_me` itself | Each stop's Contextual Source lookup uses that stop's own actual topic(s) (a heritage stop can carry more than one), deduplicated by source id - not the literal route-level `surprise_me` value, which would otherwise match nothing for every stop | N/A |
| No relevant Contextual Source for a stop's topic | e.g. a `public_art` stop (no seed entry tagged `public_art`) | `get_contextual_sources()` returns `[]`; stop is generated from its own excerpt alone - not an error | N/A |

## Tasks & Acceptance

**Execution:**
- [x] `ai.py` -- `load_contextual_sources(path=CONTEXTUAL_SOURCES_PATH)` + `get_contextual_sources(stop, topic)`: filters loaded sources by `topic in entry["topics"]`, returns `{source_type, source_title, source_url, text}` entries (keeps `id` on the internal dict for traceability, per Codex's note - external callers use the other four fields)
- [x] `ai.py` -- `check_grounding(generated_text, source_texts)`: the prototyped rule-based pre-filter, ported verbatim - extracts 3-4 digit numbers and 2+-word capitalized-phrase runs (sentence-ending punctuation breaks a run, commas don't), punctuation-normalizes both sides before substring comparison. No overlap-ratio gate. Generic signature so Epic 3 can reuse it unchanged
- [x] `ai.py` -- `check_grounding_semantic(generated_text, source_texts)` + `_call_grounding_check_batch(items)`: the real (LLM-based) gate, added after Codex proved the rule-based check insufficient (user's explicit choice - see Design Notes). One batched call per route for everything that survives the pre-filter; the single-item wrapper is what Epic 3 calls for one walk summary, still exactly one API call
- [x] `ai.py` -- `_call_content_generation(stops_with_evidence, topic)`: one batched OpenAI call. Request payload keys each stop by `stop_id` with its OWN evidence list only (each evidence entry carries an `id` - `"own"` for the stop's own source, the real seed-file id for a Contextual Source). Forced JSON response `{"stops": [{"stop_id", "content", "used_evidence_ids"}, ...]}` - `used_evidence_ids` is what makes attribution reflect sources actually drawn from (Codex review), not merely offered
- [x] `ai.py` -- `generate_stop_content(stops, topic)`: the real orchestrating function Story 1.4 will call. Builds each stop's evidence via `_lookup_topics_for_stop()` (the stop's own topic(s) for `surprise_me`, the single requested topic otherwise - Codex review) + `get_contextual_sources()`. Two-tier check: `check_grounding()` pre-filters (fail -> immediate fallback, no semantic call spent); everything that passes is batched into one `_call_grounding_check_batch()` call, whose verdict is authoritative (any failure to get a positive verdict - semantic "not supported", or the call itself failing - falls back, never trusts the pre-filter alone). Attribution built from `used_evidence_ids` ∩ what was actually offered, always including the stop's own source. Never raises - every failure mode has a defined fallback
- [x] `tests/test_ai.py` -- 30 new tests: rich/thin excerpts pass the pre-filter; the pre-filter's documented gap pinned as a regression test (and confirmed the semantic check catches exactly those two counterexamples); whole-call and semantic-call failures fall back; one missing `stop_id` isolated to that stop; two-stop batch with one unmatched topic; hand-constructed cross-stop leakage (isolated from the separate Contextual Source mechanism, checked via a marker unique to the other stop's own excerpt); `surprise_me` multi-topic lookup; attribution reflects declared-used sources only, and ignores a declared id that was never actually offered
- [x] `import_heritage.py` -- unrelated to this story's own scope, but fixed in passing (Codex review 2026-10-20, user's explicit "fix now"): `main()` now aborts if any approved heritage id lacks a topic override entry, so a missing override file can never silently report a successful import while erasing Story 1.2's topic coverage

**Acceptance Criteria:**
- Given a real batched request across stops with different topics, when `generate_stop_content()` runs, then no stop's attribution or grounding verdict is ever influenced by another stop's evidence in the same batch
- Given the grounding checks are reused for Epic 3 later, when called with arbitrary generated text and a source-text list unrelated to any Stop, then both work identically - no Stop-shaped assumption anywhere in either

## Design Notes

**Grounding-check prototype (this session, before writing this spec): three independent live runs, 6/6 correct every time**, using real `select_stops()`/`_call_openai()`-style calls (not mocked) against: the two real thin excerpts this story's AC names verbatim (`"By Michael Snape."`, `"church in Newtown, New South Wales"`), two real rich heritage excerpts (Newtown Railway Station, NSW AECG Office), and two hand-fabricated bad examples (an invented 1887 date + invented architect name; an invented 2019 date + invented research backstory) - both correctly failed on every run.

Two real bugs found and fixed during prototyping, not left in the final design:
1. A naive "skip the first capitalized word of each sentence" heuristic broke on typographic punctuation (a curly quote prevented a real sentence boundary from being detected), causing a false "unsupported" flag on an ordinary sentence-opener. Fixed by explicitly treating `.!?` as hard run-breaks in the phrase extractor, while a comma stays a soft separator (`"Newtown, New South Wales"` must still match `"Newtown New South Wales"`).
2. The stop's own real `name` wasn't included as legitimate grounding material, so content that correctly referred to a stop by its own name (e.g. "Newtown Baptist Church") got flagged as fabricating that name. Fixed by including the stop's `name` in the evidence set passed to the check, alongside its `source_excerpt`.

**Final validated design:** extract 3-4 digit numbers and 2+-word runs of capitalized words (not single capitalized words - those are usually just sentence-openers or ordinary capitalized nouns, not a specific claim) from the generated content; both are punctuation-normalized before a substring check against the combined, punctuation-normalized source text; content passes only if every extracted number and phrase is found. A general word-overlap ratio is computed and can be logged for visibility but is explicitly not a pass/fail gate - a thin 2-4 word source excerpt naturally produces a low overlap ratio even when genuinely grounded, since there's little source vocabulary to echo; gating on it would fail thin excerpts by construction, which is exactly the failure mode this story's AC calls out by name.

**Known, documented limitation, superseded below:** a fabricated *single-word* proper noun with no accompanying number (e.g. a lone invented surname) would not be caught by the phrase check alone, since it requires a 2+-word run - deliberate, since that's what avoids false positives on ordinary capitalized sentence-openers and common nouns. This turned out to understate the real gap considerably (see next section) - the rule-based check is now a pre-filter only, not the final word.

**Cross-stop evidence isolation (added after Codex's first review, before any implementation code was written):** the original single-stop prototype never exercised a multi-stop batch, so it couldn't have caught pooled-evidence leakage. The real implementation scopes every stop's evidence - in the generation prompt's per-stop structure, and in both grounding tiers' per-stop calls - strictly to that one stop, never the batch. Tests make this explicit with hand-constructed cross-stop leakage cases, not just trusted by design.

**The rule-based check proven insufficient, and escalated (Codex's second review, after initial implementation):** Codex produced two concrete counterexamples against the source `"By Michael Snape."` that pass the rule-based check cleanly while being completely fabricated: `"This sculpture commemorates workers killed in a factory fire."` (introduces no number or multi-word proper noun at all) and `"Michael Snape designed this church."` (reuses the one real name, but invents the entire relationship/claim). Verified directly - both do pass `check_grounding()`. This is a materially bigger gap than the single-word-name limitation documented above: the rule-based check can only ever catch fabrication that happens to introduce a *new, checkable token* (a number or multi-word name) - it has no way to evaluate whether a CLAIM is true, only whether certain tokens are present. Presented this to the user as a real tradeoff (per AD-3's own built-in "escalate to a model call if insufficient" path) rather than silently picking an approach, since it affects a core product promise and has a real cost/latency consequence. User chose: add a second, independent LLM-based semantic check.

**Semantic check design:** `check_grounding_semantic()` asks a model directly whether a piece of content's claims, relationships, and events are supported by its own evidence - not token presence, an actual judgment call, which is exactly what the rule-based approach structurally cannot do. Kept to one batched call per route (`_call_grounding_check_batch()`), same per-item evidence isolation discipline as content generation itself, so this doesn't reopen the latency cost AD-3 was originally trying to avoid by batching generation - it adds one extra ~2s-scale call per route, not one per stop. The rule-based check is kept as a free pre-filter ahead of it (skips the real check's cost for content already obviously bad on cheap grounds), but is no longer trusted as sufficient on its own; verified end-to-end (mocked) that the semantic check correctly rejects both of Codex's exact counterexamples.
